Cortex-ML: Complete Flow from Start to Final Decision
(five-signal architecture: Static, Behavioral, Memory, Network, Emulation)
==================================================================
Status summary before the flow: which signals actually run today
==================================================================
Not all five signals are wired the same way. This matters more here than it
did for the two-signal design, so it is stated up front rather than only in
the appendix:

  Cortex-Static      LIVE. Runs on every scan.
                     STALE BELOW -- FLAG FOR DOCS PASS (2026-09-08): every
                     description in this file of "static BLOCK -> final
                     BLOCK immediately / uncapped autonomous authority" is
                     now out of date. policy_engine.decide() interim-caps a
                     static BLOCK verdict to a final ALERT (see its "INTERIM
                     CAP" docstring); pipeline.scan() now also runs
                     behavioral on a static BLOCK. Nothing in decide()
                     returns FinalDecision.BLOCK. Full docs pass pending
                     alongside README.md / PROJECT_HISTORY_REPORT.md.
                     KNOWN ISSUE (2026-08-28, unresolved): a 57-file
                     validation round found the deployed Platt calibrator
                     collapses into two bands (~0.006 / ~0.996) and a
                     confirmed benign file outranked confirmed malware in
                     the collapsed high band. Static's BLOCK authority
                     should not be trusted until this is fixed and
                     re-validated. See "Known limitation" box after step 6.

  Cortex-Behavioral  LIVE. Runs after a static ALLOW, ALERT, or BLOCK
                     verdict (not after a static scan ERROR). Needs an
                     API-call trace with >= 10 calls; with 0-9 calls the
                     behavioral verdict stays PENDING. A verdict from a
                     10-99 call trace is emitted but flagged
                     "behavioral_short_trace" in the scan audit trail.

  Cortex-Memory      LIVE. Runs independently of every other signal --
                     unconditionally, whenever memory features are
                     supplied, even if the file path is invalid or the PE
                     fails to parse. Its MALICIOUS verdict is capped at
                     ALERT; it can never autonomously BLOCK or TERMINATE.

  Cortex-Network     TRAINED AND THRESHOLDED, NOT YET WIRED. The policy
                     engine (decide()) already accepts a network verdict
                     and caps it at ALERT, but inference/pipeline.py's
                     scan() has no network-feature input and no code path
                     that calls the trained model. Today, network_verdict
                     is always NOT_PROVIDED in a real scan call.

  Cortex-Emulation   TRAINED AND THRESHOLDED, TELEMETRY-ONLY, NOT WIRED.
                     Deliberately excluded from decide() by design (an
                     ablation-confirmed Jan->Apr 2022 concept-drift
                     collapse in malicious recall, and only a ~3-4pp edge
                     over a trivial lookup baseline). Not called from
                     scan() at all. Exists to be scored offline for later
                     analysis, not to influence any decision.

The flow below walks through what a real scan() call does today, in
execution order, and calls out each signal's actual wiring status inline.

------------------------------------------------------------------
0. CORTEX-MEMORY (runs first, independent of everything below)
------------------------------------------------------------------

Current prototype: caller passes a numpy feature vector extracted from a
memory dump (62 raw + derived features, per CIC-MalMem-2022's schema),
alongside (or instead of) a file path.

Deliberately NOT gated behind path validation, PE validation, or the static
verdict, and NOT skipped if those steps fail or are never reached. Cortex-
Memory's purpose -- catching injected or fileless malicious activity -- by
definition has no on-disk file for steps 1-6 to evaluate, so gating it
behind them would defeat the one threat class it exists to catch.

  memory_features supplied?
        |
        +-- No  -> memory verdict = NOT_PROVIDED
        |
        +-- Yes -> Cortex-Memory LightGBM + Platt calibration
                   -> memory score (0-1)
                   -> score >= 0.0005358335957155212 ?
                         +-- Yes -> MALICIOUS  (capped at ALERT downstream)
                         +-- No  -> BENIGN

  KNOWN CAVEAT: trained and threshold-derived only against CIC-MalMem-2022,
  a fixed, single-baseline-VM lab corpus. 22 of its 62 features individually
  exceed 0.95 AUC alone, consistent with the benign class being repeated
  captures of one baseline machine rather than diverse real systems -- the
  near-perfect held-out metrics (AUC-ROC 1.0, FPR 1.13%) may partly reflect
  "does this look like that one VM," not "is malicious behavior present."
  This is exactly why its ceiling is capped at ALERT and not raised, even
  though the numbers look strong.

------------------------------------------------------------------
1. FILE OR PROCESS EVENT
------------------------------------------------------------------

Current prototype: caller provides a file path directly to
CortexPipeline.scan(file_path, api_calls_json_path=None, memory_features=None).
Example: /home/tnids/notepadd.exe

There is no packaged CLI or Windows agent yet in this repo (unlike the
prior cortex-endpoint project, which shipped scan / scan-behavioral /
scan-combined as a PyInstaller .exe). cortex-ml is currently a Python
library; wrapping it behind an equivalent CLI is an open item.

------------------------------------------------------------------
2. BASIC INPUT VALIDATION
------------------------------------------------------------------

  - Does the path exist?
  - Is it a file, not a folder?
  - Can its size be read?
  - Is its size 100 MiB (104,857,600 bytes) or less?

        Validation passes            Validation fails
              |                             |
              v                             v
      (continue to step 3)          static verdict = ERROR
                                      reason code: one of
                                      path_not_found / not_a_file /
                                      unreadable / file_too_large
                                            |
                                            v
                                 policy engine still runs with
                                 whatever memory verdict step 0
                                 already computed -> see step 9
                                            |
                                            v
                                 final decision = ALERT
                                 (fail-closed default; unless memory
                                 already forced something worse, but
                                 memory's ceiling is ALERT too, so the
                                 practical floor here is always ALERT)

------------------------------------------------------------------
3. WINDOWS PE VALIDATION (rule-based, not an ML prediction)
------------------------------------------------------------------

The extractor reads the real file bytes and checks whether they parse as a
valid Windows Portable Executable (MZ/PE headers, machine type, optional
header, sections).

        Valid Windows PE              Invalid / non-PE file
              |                             |
              v                             v
      (continue to step 4)          static verdict = ERROR
                                     reason code: invalid_or_non_pe_file
                                            |
                                            v
                                 final decision = ALERT (fail-closed)

A PDF, image, plain-text file, or non-Windows binary never reaches the
LightGBM model -- it fails here, the same as in cortex-endpoint.

------------------------------------------------------------------
4. FILE PREPARATION
------------------------------------------------------------------

  - Read file bytes
  - Compute SHA-256
  - (PE already parsed in step 3; the parsed structure is reused)

------------------------------------------------------------------
5. STATIC FEATURE EXTRACTION
------------------------------------------------------------------

Convert the PE file into a 2,568-dimensional EMBER2024-compatible vector
(features/pe_features.py): byte histogram, byte entropy, printable strings,
PE header fields, section stats, imports, exports, data directories, rich
header, authenticode/certificate information, PE-parser warning flags.

  KNOWN GAP: cortex-ml has no automated feature-parity test against a
  reference extractor (cortex-endpoint has one, verified byte-exact against
  a pinned thrember install). This gap already caused one real, silent bug:
  pe_features.py imported an authenticode API (SignedPEFile) that a signify
  library upgrade (0.9.2) had removed; the import failure was swallowed
  silently, and the entire 8-dimension authenticode feature group returned
  zero for every file -- including signed Microsoft binaries -- for an
  unknown period, inflating their static scores. Caught only by manually
  comparing a 5-file scan against cortex-endpoint's output and noticing
  svchost.exe (a signed Microsoft binary) scored 0.99 here vs 0.47 there.
  Fixed (ported to signify's current AuthenticodeFile/iter_signatures() API)
  but the underlying feature-parity fidelity gap this exposed -- cortex-ml's
  vector still skews more "malicious" than thrember's on real files -- is
  still open. Building the missing parity test is the top item on the
  static-path open-issues list.

------------------------------------------------------------------
6. CORTEX-STATIC LIGHTGBM MODEL
------------------------------------------------------------------

  Input:  2,568 numerical features
  Output: calibrated static maliciousness score between 0 and 1
          (Platt-calibrated probability, chained into the model itself
          for the ONNX export -- see below)

Static verdict selection:

  Static score
       |
       +-- Score <  0.6163460957                  -> ALLOW
       |
       +-- Score >= 0.6163460957 and < 0.9950119117 -> ALERT
       |
       +-- Score >= 0.9950119117                   -> BLOCK

Examples:
  Static score 0.30  -> ALLOW
  Static score 0.80  -> ALERT
  Static score 0.995 -> BLOCK

+----------------------------------------------------------------+
| KNOWN LIMITATION -- Cortex-Static calibration, UNRESOLVED       |
| (found 2026-08-28, downgrades production-readiness):            |
|                                                                  |
| A 57-file validation round found the deployed score collapses    |
| into two bands (benign ~0.006, malicious ~0.996) with almost     |
| nothing in between, and a confirmed cross-over: a benign file    |
| (extractor.exe, calibrated 0.9956) outranked two confirmed-      |
| malicious samples sitting just above BLOCK. Two compounding      |
| causes: (a) the feature-parity gap above inflates raw margins    |
| for some real benign files into moderate-positive territory;     |
| (b) the Platt calibrator was fit unregularised on an already     |
| near-perfectly-separated probability distribution, making it a   |
| near-step function that maps any moderate-positive raw margin    |
| to a near-1.0 calibrated score and destroys rank order exactly   |
| in the ALERT-adjacent zone where real files interleave.          |
|                                                                  |
| Consequence: Static's BLOCK verdict -- the one autonomous,       |
| uncapped decision in the whole policy engine -- should not be   |
| trusted until both causes are fixed and the model is             |
| re-validated on a real-world, confirmed-label file set. No       |
| threshold change fixes this; it only relocates the band, it      |
| does not restore the lost resolution. Full margin/probability/   |
| calibrated-score table is in README.md and                       |
| PROJECT_HISTORY_REPORT.md (Step 3).                              |
+----------------------------------------------------------------+

What happens after static analysis?

  Static verdict
        |
        +-- BLOCK  -> final decision = BLOCK immediately, nothing else
        |            is consulted (see the calibration caveat above --
        |            this is the one verdict in the whole system that
        |            currently cannot be overridden by anything)
        |
        +-- ALERT  -> proceed to behavioral if API-call data is supplied;
        |            static's ALERT is preserved unless behavioral
        |            upgrades it to TERMINATE
        |
        +-- ALLOW  -> proceed to behavioral if API-call data is supplied
        |
        +-- ERROR  -> never proceeds to behavioral; final decision = ALERT

(This differs from a stricter "only ALLOW proceeds" reading some project
docs use as shorthand: the actual code runs behavioral for both ALLOW and
ALERT, and only skips it for BLOCK and ERROR -- BLOCK because it is already
final and protected, ERROR because there is no reliable static evidence to
combine it with.)

------------------------------------------------------------------
7. BEHAVIORAL INPUT
------------------------------------------------------------------

Current input: path to a JSON file containing an ordered list of Windows
API-call names. Example: /tmp/sample_calls.json

Example JSON:
  ["OpenProcess", "VirtualAllocEx", "WriteProcessMemory", "CreateRemoteThread"]

Same as before, live telemetry capture is not implemented -- the sequence
must be supplied separately.

------------------------------------------------------------------
8. BEHAVIORAL PREPROCESSING
------------------------------------------------------------------

  API-call JSON path
        |
        v
  Read and validate JSON (must be a flat list of strings)
        |
        v
  Convert every API name to a token ID (unknown names -> <UNK>)
        |
        v
  Use at most the first 100 API calls

  Sequence length              Status         Behavioral verdict
  ------------------------     -----------    -------------------
  0 API calls                  "empty"        PENDING
  1-9 API calls                 "too_short"    PENDING (model is non-
                                                discriminative below 10 calls:
                                                val+test AUC 0.66, 0/4 caught)
  10-99 API calls               "short"        scored on the padded sequence;
                                                verdict emitted, and the scan
                                                reason_codes get
                                                "behavioral_short_trace"
                                                (test AUC 0.9921, 0 FP on 118
                                                benign short rows)
  exactly 100 API calls         "ok"           scored normally
  more than 100 API calls       "truncated"    scored on first 100 only
                                                (remainder ignored)

------------------------------------------------------------------
9. CORTEX-BEHAVIORAL 1D-CNN + ATTENTION MODEL
------------------------------------------------------------------

  Input:  100 numerical API-call token IDs
  Output: behavioral maliciousness score between 0 and 1 (sigmoid)

Behavioral verdict selection:

  Behavioral score
       |
       +-- Score <  0.60  -> BENIGN
       +-- Score >= 0.60  -> MALICIOUS

Examples:
  Behavioral score 0.30  -> BENIGN
  Behavioral score 0.59  -> BENIGN
  Behavioral score 0.60  -> MALICIOUS

+----------------------------------------------------------------+
| KNOWN LIMITATION -- one persistent, understood false positive:  |
| across the full validation+test sweep, exactly one benign       |
| sample (networking-setup calls: setsockopt, ioctlsocket,        |
| wsastartup, getsockname, alongside routine registry/system      |
| calls -- plausibly confusable with C2 setup) scores 0.921006,   |
| confidently wrong, at every threshold below ~0.922. The         |
| threshold was deliberately kept at 0.60 rather than raised past |
| 0.922 to clear this single case: n=1 isn't sound evidence for a |
| permanent recall tradeoff, and behavioral has no rule-based     |
| backstop yet for high-risk call combinations independent of the |
| ML score.                                                       |
+----------------------------------------------------------------+

Like Static, the behavioral model does not produce ALERT or BLOCK
directly -- only BENIGN or MALICIOUS. The policy engine turns a MALICIOUS
behavioral verdict into TERMINATE.

------------------------------------------------------------------
10. CORTEX-NETWORK AND CORTEX-EMULATION (status, not live flow)
------------------------------------------------------------------

Both models are fully trained and threshold-derived, and both have a
verdict enum and a *_verdict_from_score() function in
inference/policy_engine.py -- but neither is reachable from a real
CortexPipeline.scan() call today:

  Cortex-Network (LightGBM + Platt, CSE-CIC-IDS2018 flow features):
    threshold 0.9441855970306654 -> MALICIOUS, capped at ALERT.
    decide() already has a network_verdict parameter and branch for it,
    but pipeline.scan() has no network-feature argument and never calls
    the trained model -- so in practice network_verdict is always
    NOT_PROVIDED and this branch is currently unreachable in a live scan.
    KNOWN CAVEATS even once wired: only 10.75% detection on Infiltration
    attacks (a documented CICFlowMeter feature-representation ceiling, not
    an under-training artifact), and CSE-CIC-IDS2018 has independently
    reported ~7.5% label noise plus a documented pattern of "nearly
    perfect" models on this dataset collapsing on external traffic.

  Cortex-Emulation (1D-CNN + attention, Speakeasy module-entry traces):
    threshold 0.999358594417572, LOGGING/TELEMETRY ONLY. Deliberately not
    given a decide() branch at all (by design, not an oversight) and not
    called from pipeline.scan(). An ablation-confirmed Jan->Apr 2022
    concept-drift collapse (malicious recall 70.7% -> 41.5%) and only a
    ~3-4 percentage-point edge over a trivial duplicate-lookup baseline
    mean it cannot yet carry even ALERT authority.

------------------------------------------------------------------
11. POLICY ENGINE -- FINAL DECISION LOGIC
------------------------------------------------------------------

Scores are never averaged or ensembled. Verdicts are combined by a fixed
priority order (inference/policy_engine.py::decide()):

  1. Is the static verdict BLOCK?
        +-- Yes -> final decision = BLOCK   (always protected; see the
        |          Cortex-Static calibration caveat in step 6 -- this is
        |          the one verdict nothing else can override)
        +-- No, continue
  2. Is the behavioral verdict MALICIOUS?
        +-- Yes -> final decision = TERMINATE
        +-- No, continue
  3. Is the memory verdict MALICIOUS?
        +-- Yes -> final decision = ALERT   (capped -- never autonomous
        |          BLOCK/TERMINATE; see step 0's caveat)
        +-- No, continue
  4. Is the network verdict MALICIOUS?
        +-- Yes -> final decision = ALERT   (capped; currently
        |          unreachable -- see step 10, network isn't wired yet)
        +-- No, continue
  5. Is the static verdict ALERT?
        +-- Yes -> final decision = ALERT
        +-- No, continue
  6. Did static scanning fail (ERROR)?
        +-- Yes -> final decision = ALERT
        +-- No, continue
  7. Did behavioral scanning fail (ERROR)?
        +-- Yes -> final decision = ALERT
        +-- No, continue
  8. Did memory scanning fail (ERROR)?
        +-- Yes -> final decision = ALERT
        +-- No, continue
  9. Did network scanning fail (ERROR)?
        +-- Yes -> final decision = ALERT
        +-- No, continue
  10. Otherwise -> final decision = ALLOW

Complete decision table (Static x Behavioral -- the two signals that are
both live and mutually gated; Memory/Network sit alongside this table as
independent additive checks per the priority order above, not crossed
into it, since a scan can produce any Memory/Network verdict regardless of
what Static/Behavioral produced):

  Static result   Behavioral result   Final decision
  -------------   -----------------   --------------
  Allow           Not provided        Allow
  Allow           Pending             Allow
  Allow           Benign              Allow
  Allow           Malicious           Terminate
  Allow           Error               Alert
  Alert           Not provided        Alert
  Alert           Pending             Alert
  Alert           Benign              Alert
  Alert           Malicious           Terminate
  Alert           Error               Alert
  Block           Any result          Block
  Static error    (behavioral never runs; verdict stays Not provided)  Alert

Then, independent of the row selected above: a Memory or Network MALICIOUS
verdict upgrades an would-be ALLOW to ALERT (but can never reach BLOCK or
TERMINATE), and a Memory or Network ERROR upgrades an ALLOW to ALERT too --
neither can downgrade a BLOCK or a behavioral-driven TERMINATE, since those
are checked first in the priority order.

------------------------------------------------------------------
12. FINAL OUTPUT
------------------------------------------------------------------

Final policy decision
        |
        v
  Structured JSON security event (ScanResult.to_dict(), wrapped by
  to_security_event() with a timestamp and correlation ID added):

    {
      "file_path": ...,
      "sha256": ...,
      "static":     {"score": ..., "verdict": "ALLOW|ALERT|BLOCK|ERROR"},
      "behavioral": {"score": ..., "verdict": "NOT_PROVIDED|PENDING|BENIGN|MALICIOUS|ERROR"},
      "memory":     {"score": ..., "verdict": "NOT_PROVIDED|BENIGN|MALICIOUS|ERROR"},
      "network":    {"score": ..., "verdict": "NOT_PROVIDED|BENIGN|MALICIOUS|ERROR"},
      "final_decision": "ALLOW|ALERT|BLOCK|TERMINATE",
      "reason_codes": [...],
      "timestamp": ...,
      "correlation_id": ...
    }

Note there is no "emulation" key in this event at all today -- consistent
with it being purely out-of-band telemetry, not part of the decision or
even the decision's audit record.

Possible final decisions:
  ALLOW      -- no sufficiently strong malicious evidence from any live
               signal
  ALERT      -- suspicious result from Behavioral (via static gate),
               Memory, or Network, or a scanner failure needing review
  BLOCK      -- static score crossed the strict block threshold (subject
               to the calibration caveat in step 6)
  TERMINATE  -- the behavioral model identified malicious API-call
               activity

As with cortex-endpoint, these are currently only JSON decisions -- this
package does not itself allow, block, quarantine, or terminate anything at
the OS level, and there is no packaged Windows agent or CLI yet.

==================================================================
Team-ready explanation
==================================================================

The architecture begins with Cortex-Memory, which runs on whatever memory
features are supplied completely independently of the file path -- it has
no dependency on a valid on-disk file, because its purpose is to catch
injected or fileless activity that structurally never has one. Everything
else starts when the application receives a Windows executable file path.
It performs normal validation (path exists, readable, within the size
limit) and confirms a valid Windows PE structure; either failure produces a
static ERROR and a fail-closed ALERT. If valid, it extracts a 2,568-feature
EMBER2024-compatible vector and passes it to the Cortex-Static LightGBM
model, which produces an ALLOW, ALERT, or BLOCK verdict -- currently the
one verdict in the whole system that can unilaterally decide the outcome,
and also the one flagged with an unresolved calibration issue as of
2026-08-28. Unless that verdict is BLOCK, and if an API-call sequence is
supplied, the first 100 calls are tokenized and scored by the Cortex-
Behavioral 1D-CNN+Attention model, producing BENIGN or MALICIOUS. The
policy engine never averages any of these scores; it combines verdicts by
fixed priority -- static BLOCK always wins, behavioral MALICIOUS becomes
TERMINATE, and a MALICIOUS verdict from Memory (or, once wired, Network)
can only ever raise the outcome to ALERT, never higher. Two more models --
Cortex-Network and Cortex-Emulation -- are fully trained and have derived
thresholds, but neither is connected to a live scan yet: Network's policy
logic exists and is waiting on a feature-input path, while Emulation is
intentionally kept out of the decision entirely and exists only for
offline telemetry, pending a fundamentally different model given its
documented concept-drift collapse. The system produces a structured JSON
security event either way, though -- as with the prior project -- live
telemetry collection, a packaged agent/CLI, and actual OS-level blocking or
termination are not yet implemented.

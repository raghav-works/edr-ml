Section 1

Executive Summary

In plain terms

Cortex is a Windows malware detector that looks at a suspicious program in five independent ways instead of relying on a single test. Each of the five "signals" examines a different kind of evidence: the file's structure on disk, the sequence of system actions it performs, what it looks like in a computer's memory, the network traffic it generates, and how it behaves inside a safe emulator. The five results are then combined by a rule-based policy engine that follows a strict priority order — it never averages scores together.

Why five and not one? Because every single detection method has a blind spot. A file that is disguised on disk may still act maliciously once running. Fileless malware never writes a file to disk at all, so only the memory signal can see it. Slow, quiet intrusions hide from network analysis but show up in system-call behavior. Using five overlapping signals means one signal's weakness is covered by another's strength.

Headline results: the two most-trusted signals (Static and Behavioral) score AUC 0.997–0.999 across three separate implementations and have been checked against real malware and real signed Microsoft tools. Two newer signals (Memory and Network) are fully trained with strong lab metrics but are deliberately held back from the most severe automated actions until they are validated on real-world data. The fifth signal (Emulation) is trained but kept out of decisions entirely because testing exposed a serious accuracy collapse over time.

Technical detail

What Cortex is. cortex-ml is a from-scratch, independently engineered reproduction of a malware-detection architecture previously proven across two earlier repositories (malware-ml, the research phase, and cortex-endpoint, a packaged Windows executable). The prior work hit AUC > 0.998 static and AUC > 0.99 behavioral and passed real-world validation against live malware samples and signed system tools. cortex-ml reproduces that detection logic in a footprint small enough to hand to another team, began with two signals (Static, Behavioral), and has since been extended to five.

Why five independent signals. The architecture contract (Architecture.txt) specifies sequential gating with no ensembling: signals are combined by fixed-priority verdict rules, never by averaging scores. Each signal exists because it sees a threat class the others structurally cannot:

  • Static — catches known-bad file structure before anything executes, but is blind to a clean-looking file that turns malicious at runtime.
  • Behavioral — catches malicious runtime API-call patterns, but needs an execution trace to exist.
  • Memory — catches injected code and fileless malware that never write a file to disk, so there is nothing for Static to score.
  • Network — catches malicious traffic patterns (DDoS, brute force, botnet C2) from flow statistics alone.
  • Emulation — catches malicious behavior inside a Speakeasy emulator before the sample ever runs on a real host.

What is fully trusted vs. still being validated — one honest paragraph

Static (BLOCK) and Behavioral (TERMINATE) carry full autonomous authority: both are validated across three independent implementations with consistently strong AUCs, and Static passed real-world checks against actual malware and signed Microsoft tools. Memory and Network are real, fully-trained, ONNX-exported signals with excellent held-out metrics, but each is deliberately capped at ALERT for its own specific, diagnosed reason — Memory because its benign training data all comes from a single baseline virtual machine (22 of 62 features separate the classes almost perfectly, which looks more like "recognising that one VM" than "recognising malice"); Network because it detects only 10.75% of slow "Infiltration" attacks and because models that look near-perfect on its training dataset are documented to collapse toward random on real traffic. Emulation is trained but held report-only: an ablation confirmed its malware recall falls from ~71% to ~42% between the January and April 2022 collection eras and that shrinking the model does not fix it, and it beats a trivial lookup-table baseline by only ~3–4 percentage points. Separately, a recently found static feature-extraction bug (a broken optional signify import that silently zeroed one feature group) has been partially fixed, but the residual feature-fidelity gap versus the reference extractor and the absence of an automated parity test remain the top open correctness item for the static path.

Section 2

System Architecture — What Happens When a File Comes In

In plain terms

When a file arrives, Cortex runs a fixed sequence of checks. First it makes sure the file is real, readable, not too large, and actually a Windows program. Then it converts the file into a long list of numeric measurements and asks the Static model for a verdict: allow, alert, or block. A block is final and everything stops. An allow or alert lets the file move on to the Behavioral model, if a record of the program's actions is available.

The Memory check is different: it runs on its own, in parallel, and is not made to wait behind the file checks. That is deliberate — fileless malware never creates a file on disk, so if Memory had to wait for a valid file to be found, it would never get to examine exactly the threat it exists to catch. The Network check is defined in the decision rules but is not yet connected into the scan pipeline itself; this report says so plainly rather than implying it is live. Finally, every result is passed to the policy engine, which applies its priority rules and produces one final decision plus a structured JSON event record.

Step-by-step walkthrough (CortexPipeline.scan())
  1. Memory first, deliberately (step 7 in code order). If a memory feature vector is supplied, Cortex-Memory runs before any file validation and independently of it. This is intentional: a fileless / injected threat has no on-disk file to resolve, so gating Memory behind path or PE validation would disable it for exactly the threat class it exists to catch.
  2. Path validation. _validate_path() checks the path exists, is a regular file, is readable, and is ≤ 100 MiB (MAX_FILE_SIZE_BYTES). On failure the static verdict becomes ERROR, a reason code is recorded, and the policy engine is called immediately with whatever verdicts exist (Memory may still have produced one).
  3. Rule-based PE validation. feature_extractor.is_valid_pe(bytez) — a structural check, not an ML prediction. A non-PE or corrupt file yields static_verdict = ERROR and reason code invalid_or_non_pe_file, then straight to the policy engine.
  4. SHA-256 + feature extraction. The file's SHA-256 is recorded and PEFeatureExtractor.feature_vector() produces the 2568-dimensional EMBER2024-compatible vector (12 feature groups; see §3.1).
  5. Static model. static_model.predict_proba() returns a single Platt-calibrated malicious probability. static_verdict_from_score() maps it: < 0.6163460957 → ALLOW; < 0.9950119117 → ALERT; otherwise → BLOCK. Any exception here is caught and becomes static_verdict = ERROR with reason static_scan_exception — it is never allowed to crash the scan or silently pass.
  6. Gate into Behavioral. If static_verdict == ALLOW and an API-call JSON path was supplied, Behavioral runs. If static_verdict == ALERT and API-call JSON was supplied, Behavioral also runs (an ALERT can still be upgraded to TERMINATE by a MALICIOUS behavioral verdict). If static_verdict == BLOCK, Behavioral is never run — the block is already protected and final. The tokenizer returns PENDING for empty / insufficient traces rather than guessing.
  7. Memory in parallel (already computed in step 1). Its score and verdict sit alongside the static and behavioral verdicts with no dependency between them.
  8. Network — current wiring status, stated honestly. NETWORK_MALICIOUS_MIN, NetworkVerdict, and network_verdict_from_score() all exist in inference/policy_engine.py, and decide() accepts a network_verdict argument. But CortexPipeline.scan() has no network parameter and never computes or passes a network verdict — the pipeline was never extended. Network is a trained, ONNX-exported model with a derived threshold; it is simply not yet called end-to-end.
  9. Policy engine. decide(static_verdict, behavioral_verdict, memory_verdict[, network_verdict]) applies the priority chain in §4 and returns a FinalDecision plus reason codes.
  10. Structured output. to_security_event() wraps the result as a JSON envelope with a UTC timestamp and a UUID correlation ID: per-signal {score, verdict} blocks, the final decision, and the accumulated reason codes.
Why some signals gate on others and some do not

Static → Behavioral is gated because Behavioral analysis exists to refine an uncertain static result. A static BLOCK is already the most severe file-level verdict and is unconditionally final, so running Behavioral after it would add cost and risk (a MALICIOUS→TERMINATE upgrade is possible but a BLOCK already stops the file). An ALLOW or ALERT is where a second opinion has value, so the gate opens there.

Memory does not gate because its target — injected code and fileless malware — by definition leaves no valid on-disk PE for steps 1–4 to evaluate. If Memory waited behind static validation, a fileless intrusion that fails PE validation (there is no PE) would never be examined. So Memory runs whenever memory features are supplied, regardless of the static verdict and even when path/PE validation failed outright.

Network, once wired, is designed to be independent for the same reason: network flows exist whether or not a file was submitted for scanning, and the threats it targets (C2 beaconing, exfiltration, floods) are not tied to a single on-disk artifact.

Fail-closed everywhere. Every validation failure and every caught scan exception resolves to ERROR, and decide() maps every ERROR to ALERT — never to a silent ALLOW.

Per-Signal Deep Dive

Each subsection follows the same shape: a plain-language summary, then what the signal detects and why it is separate, the real dataset and its provenance/licensing, the architecture chosen and why (including where it deliberately diverged from a reference design and the evidence for that), how the threshold was derived, and the current measured performance.

3.1   Cortex-Static

In plain terms

Static analysis looks at a Windows program without running it. It measures thousands of structural properties of the file — its headers, sections, imported functions, embedded strings, byte patterns, digital signature — and a gradient-boosted decision-tree model decides how malicious that structure looks. This is the fastest signal and the only one that can act with full authority: a Static BLOCK is always final. It is trained on EMBER2024, a large public research dataset of labelled Windows programs.

What it detects and why it is a separate signal

Malicious PE file structure — packers, anomalous headers, suspicious import tables, known-bad string/IOC patterns, signature anomalies — detectable before any execution. It is the first line of defence and the only signal with no execution-trace dependency, so it is the natural place for the highest-authority verdict.

Dataset & provenance

EMBER2024, streamed from HuggingFace (FutureComputing4AI/EMBER2024-derived), Apache-2.0, PE-format records only. datasets.load_dataset() hit an Arrow schema-inference crash on this dataset, so data/download_ember2024.py streams the PE records directly from the HF zips and deduplicates on sha256 in bounded batches. The raw download contained every row twice (~50% duplicate rate, the signature of "every sample present twice"): 4,680,000 raw train rows → 2,340,000 unique; 1,080,000 raw test rows → 539,940 unique. Leakage check: zero train/test hash overlap after the dedup fix (a handful of within-test-shard repeats noted, not train/test crossing).

Architecture chosen, and why

LightGBM gradient-boosted trees over the 2568-dim feature vector, with a Platt calibrator (LogisticRegression) fitted on top of the raw booster. Hyperparameters: num_leaves=255, max_depth=15, learning_rate=0.03, min_child_samples=50, is_unbalance=True. Training used 2,996 boosting rounds, ~2.1h wall time. Trees are the established architecture for EMBER-family tabular features and are unaffected by input scaling.

Divergence from the reference, and the evidence for it. Two deliberate departures:

  • Feature extractor rewritten for formula-fidelity, not copied. features/pe_features.py matches the real EMBER2024 / "thrember" reference extractor's group budget and formulas exactly (fixed string-regex vocabulary, header categorical dictionaries, section stats, data-directory layout, hashing schemes) — replacing an earlier version built from independently-guessed field semantics. The reason: a live PE-byte vector and an EMBER2024 training record must be numerically column-compatible, or the model learns one semantics at training time and is fed another at inference — a skew that does not show up in offline eval. Every field inside each group was still chosen independently; this is a formula-compatible reimplementation, not a line-for-line port.
  • Memory pressure solved with OS swap, not data subsampling. Training on the full 2.34M-row / 2568-feature split repeatedly OOM-killed a 38 GB machine. Fixes applied in order: a streaming train/val loader instead of a full fancy-indexed DataFrame, free_raw_data=True + explicit del/gc.collect(), reduced n_jobs, a capped histogram_pool_size, two-round Dataset construction — and finally adding swap space at the system level. The earlier research repo, under the same class of memory pressure, instead trained on a 51.3% subsample; a separate attempt there at sequential chunked training was explicitly rejected after validation TPR degraded across chunks (0.917 → 0.171 → 0.174). cortex-ml trained on 100% of the deduplicated data.
Threshold derivation

STATIC_ALLOW_MAX and STATIC_BLOCK_MIN were re-derived from scratch against cortex-ml's own trained model — models.static_lgbm.find_threshold_for_fpr() run on the calibrated probabilities over the 539,940-row deduplicated EMBER2024 test split, not carried over from the prior project's placeholder values.

No INT8 quantization (tree ensembles are unaffected by weight quantization).

A silent signify 0.9.2 import failure had zeroed the entire 8-dim authenticode feature group at inference (see §5.4 and §6). It is now ported to the 0.9.x API, but a residual feature-fidelity gap versus the thrember reference remains — cortex-ml's vector is systematically shifted toward "malicious" — and there is still no automated feature-parity test. The earlier research-repo candidate also showed a PyInstaller-build-artifact false positive on a signed benign binary; this has not been re-tested against cortex-ml's own static model.

3.2   Cortex-Behavioral

In plain terms

Behavioral analysis looks at what a program actually does — the ordered list of Windows system functions it calls while running. A neural network reads that sequence and decides whether the pattern of actions looks malicious. This catches malware that is disguised well enough on disk to slip past Static but gives itself away through its behavior. A Behavioral MALICIOUS verdict can autonomously trigger the most severe action, TERMINATE.

What it detects and why it is a separate signal

Malicious runtime intent expressed as an API-call sequence (e.g. injection, persistence, C2 setup, credential access). It exists separately because a structurally clean file can still behave maliciously, and because a sequence model captures ordering and context that static structural features cannot.

Architecture chosen, and why

1D-CNN + multi-head self-attention, single sigmoid score (models/behavioral_cnn.py): token embedding + learned positional embedding → conv stack (channels 128→256→128→128, kernel sizes 3,5,7,3, each with BatchNorm + dropout 0.3) → multi-head self-attention (4 heads, residual + LayerNorm) → global pool → linear sigmoid head. Fixed sequence length 100, <PAD>/<UNK> tokens. Raw sigmoid output, no calibration layer. embed_dim defaults to 128 in the training CLI (dropping to 64 is a documented option). This follows the architecture brief's CNN + attention shape.

Divergence from the reference: the earlier research-repo behavioral model (Model A, Oliveira-sourced) used embedding → 2×Conv1D → global max pool → sigmoid with no attention. cortex-ml added the self-attention block and moved to the three-source Mal-API-2019 + MalbehavD-V1 + Carpenter corpus. The evidence that drove a more conservative overall approach is Model A's threshold-generalization failure (below).

Threshold derivation

BEHAVIORAL_MALICIOUS_MIN = 0.60. Derived by a threshold sweep (0.10–0.99) over the val+test splits combined (1,835 rows, only 274 benign) — deliberately not find_threshold_for_fpr() at a precise target, because 274 benign samples (~0.36% resolution each) cannot support a precise FPR claim. Exactly one benign sample is a persistent false positive at every threshold below ~0.922 — a MalbehavD-V1 trace with setsockopt / ioctlsocket / wsastartup / getsockname alongside routine registry/system calls, plausibly confusable with C2 setup; the model scores it 0.921006, confidently wrong. The threshold was deliberately not raised to clear this single case: n=1 is not a sound basis for a permanent recall trade-off across the whole malicious population, and Behavioral has no rule-based backstop in this repo yet. Malicious false-negative count on val+test climbs slowly as the threshold drops (57 at 0.95, 49 at 0.90, ~38 at 0.60, 36 at 0.50).

Current performance

Held-out test at threshold 0.60: accuracy 98.36%, precision 100%, recall 98.08%, AUC-ROC 0.9973. 18 epochs, early-stopped, ~4 minutes wall time on CPU. ONNX export: two bugs found and fixed — torch.onnx.export() defaulting to the dynamo exporter (needs onnxscript, not a dependency; forced legacy dynamo=False), and quantize_dynamic() trying to quantize the Conv1d stack (no ConvInteger CPU kernel; INT8 quantization restricted to MatMul/Gemm).

Known limitation

The single hard benign false positive above; no rule-based overlay for high-risk call combinations independent of the ML score (flagged as the targeted future fix, not blanket threshold tuning). And unlike the prior research-repo model, cortex-ml's behavioral threshold has not yet been stress-tested against a genuinely held-out generalization check.

3.3   Cortex-Memory

In plain terms

Memory analysis examines a snapshot of a computer's RAM for the fingerprints of malicious activity — code injected into another process, hidden modules, unusual handle or driver counts. Crucially, this works even when malware never writes a file to disk. Because of that, the Memory check runs on its own and is not made to wait for the file checks. Its metrics on the research dataset are near-perfect — which is itself a reason for caution, so its authority is capped at ALERT.

What it detects and why it is a separate signal

Injected / fileless malicious activity visible only in a memory image: process hollowing, injected regions (malfind), hidden processes (psxview), anomalous handle/DLL/callback/driver statistics. It is independent because there is often no on-disk file for any other signal to score.

Dataset & provenance

CIC-MalMem-2022 (Carrier et al., ICISSP 2022) — a public research dataset, no licensing ambiguity. The official UNB/CIC portal requires a manual download form and, at pull time (2026-08-25), was missing 3 of the dataset's 4 top-level categories; the working copy was taken from the Kaggle mirror luccagodoy/obfuscated-malware-memory-2022-cic. 58,596 rows, 55 VolMemLyzer-derived numeric memory-forensics features plus Category (family + Benign) and Class (Benign/Malware). Schema validated structurally against the real file (column count, dtypes, exact Class value set, first/last column identity), not trusted from documentation.

Architecture chosen, and why

LightGBM + Platt calibration, mirroring models/static_lgbm.py's shape exactly. Inputs: the 55 raw VolMemLyzer columns plus 7 derived ratio/aggregate features (62 total) — callbacks_anonymous_ratio, svcscan_driver_ratio, handles_file_ratio, handles_mutant_ratio, psxview_hiding_score, ldrmodules_hidden_ratio, malfind_injection_rate — each tied to a specific memory-forensics indicator. Hyperparameters: num_leaves=31, max_depth=-1, learning_rate=0.05, min_child_samples=20; is_unbalance deliberately omitted (the split is near 50/50, unlike Static). Best iteration 71 (val-driven early stopping).

Divergence / deliberate design choices: a MemoryFeatureScaler (train-only-fit standardisation) is built and tested but not applied — tree-ensemble splits are provably invariant to any monotonic per-feature transform, so scaling every value would change zero split decisions while adding a second fitted artifact to carry into the ONNX export. Handles-per-process and DLL-per-process ratios were deliberately not added as derived features because VolMemLyzer already provides them directly. The scaler stays available for a future non-tree Cortex-Memory variant.

Known limitation — the reason for the ALERT cap

22 of the 62 features individually exceed 0.95 AUC, confirmed on both the train split and the untouched test split — e.g. handles.avg_handles_per_proc is a tight 208–318 band for benign (std 17.5) but ranges 71–33,784 for malware; dlllist.avg_dlls_per_proc is 34.5–53.2 for benign but drops to 7.3 for malware. This pervasive multi-feature separability on data the model never trained on rules out our own split leaking and points at the dataset itself: every CIC-MalMem-2022 benign sample is a repeated capture of "normal user behavior" on a single baseline Windows 10 VM, while malicious samples span far more varied executions. The model may be learning "does this look like that one baseline VM" more than "is malicious behavior present." This is a specific reason to keep the ALERT cap, not a generic hedge. Also unsolved: benign near-duplicates (only exact duplicates are merged), because nothing in the schema identifies which benign rows share a capture session.

3.4   Cortex-Network

In plain terms

Network analysis looks only at statistics about network connections — how long they last, how many packets and bytes flow each way, timing between packets — never the packet contents. From those numbers a decision-tree model flags traffic that matches attack patterns like denial-of-service, brute-force login attempts, or botnet command-and-control. It is trained on a large public intrusion-detection dataset. It has a real blind spot for slow, quiet intrusions, and near-perfect scores on this kind of dataset are known to collapse on real traffic — so its authority is capped at ALERT. The model is trained and exported but not yet wired into the scan pipeline.

What it detects and why it is a separate signal

Malicious traffic patterns from CICFlowMeter flow-statistics: DDoS (HOIC/LOIC), brute force (FTP/SSH/web), botnet, DoS (Hulk/GoldenEye/Slowloris/SlowHTTPTest). Independent of any scanned file — flows exist on their own.

Dataset & provenance

CSE-CIC-IDS2018 (Sharafaldin et al., CIC), chosen over UNSW-NB15 specifically because UNSW-NB15 has a documented licensing ambiguity while CSE-CIC-IDS2018 has an explicit, clear redistribution licence. Hosted on AWS Open Data (s3://cse-cic-ids2018/, ca-central-1) with no account or access form. Only the Processed Traffic Data for ML Algorithms/ prefix was synced (10 CICFlowMeter CSVs, 6.4 GiB) — not the raw PCAPs. 16,233,002 raw rows across 10 capture days (Feb–Mar 2018).

Architecture chosen, and why

LightGBM + Platt calibration, mirroring Static/Memory exactly (split → calibrate → derive threshold from our own data → ONNX export with calibration merged). One deliberate hyperparameter deviation from Memory's config: is_unbalance=True, because Network's train split is 84.3% benign / 15.7% malicious (~5.4:1), unlike Memory's near-50/50 — blindly copying Memory's omission would have reused a choice made for a different class balance. num_leaves=31, max_depth=-1, learning_rate=0.05, min_child_samples=20. 760 boosting iterations (early stop at 760/810), 54.2 s fit, peak RSS 2.8 GiB.

Divergence from the reference: deliberately not the autoencoder + classifier hybrid some network anomaly-detection designs use — that is a legitimate future capability, not a starting point. A single-feature-AUC sweep (the same check that caught Memory's shortcut) found 0 of 78 features exceed 0.95 AUC on train or test; top feature Fwd Seg Size Min (train AUC 0.736 / test 0.848) is informative, not a giveaway — this model's performance reflects genuine multi-feature learning despite CSE-CIC-IDS2018 also being a fixed-testbed capture.

Data-quality handling (10 issues, each handled deliberately)

Non-uniform column count (the Thuesday-20-02-2018 file has 84 vs 80 — 4 leading identity columns dropped, not aligned, so a model cannot memorise which fixed testbed machine was the attacker); Timestamp excluded from features (each day is one attack scenario — a near-perfect label proxy); 59 literal header-repeat rows filtered via an allowlist of real observed labels; Flow Byts/s / Flow Pkts/s NaN/Inf rows dropped, not imputed; inconsistent label taxonomy sidestepped via case-insensitive != "benign"; two-phase memory-safe loading capped the working set at 2,000,000 rows (peak RSS 22.8 GiB, ~8.5 min). 495,181 / 2,000,000 rows (24.75%) were exact duplicates — union-merged into atomic groups before splitting. 4,742 duplicate groups spanned both benign and malicious labels (identical 78-feature vector, contradictory ground truth — a CICFlowMeter representation limit, not leakage): excluded entirely from train, val, and test (48,329 rows, 2.42%), saved separately for inspection. A real stratified_group_split index bug (writing into a plain array using non-contiguous DataFrame index values) was found and fixed with an explicit reset_index(drop=True).

Threshold derivation

NETWORK_MALICIOUS_MIN = 0.9441855970306654, via find_threshold_for_fpr() at target FPR 0.001 against calibrated val+test-combined probabilities (424,914 rows, 321,733 benign — ~0.0003% resolution per false positive, so sub-0.1% targets are defensible here, unlike Memory or Behavioral).

Current performance

Held-out test: AUC-ROC 0.9972, AUC-PR 0.9951, precision 0.9969, recall 0.9752, F1 0.9859, FPR 0.098%. Per-attack-type detection is 99.9–100% for Bot, all DDoS/DoS variants, and SSH-Bruteforce; 75–91% for the under-trained web brute-force classes; and 10.75% for Infiltration (n_test 1,433, n_train 11,463). ONNX export: mean abs error 2.1e-4, max abs error 0.5465 — three orders looser than Static's/Memory's, root-caused to the ONNX TreeEnsemble spec (LightGBM stores split thresholds as float64; ONNX's tree operator is float32-only), made visible here because Flow Duration/IAT features run up to ~1.15e8. Measured practical impact: only 3 of 213,217 predictions (0.0014%) flip at the operating threshold (two are exact boundary ties; the third is actually more correct in ONNX); aggregate metrics shift only in the 4th decimal. Shipped as the final artifact with the limitation documented.

Known limitation — the two reasons for the ALERT cap

(a) Infiltration blind spot: 10.75% detection is not under-training (every other under-10,000-train class scored ≥91% except the two duplicate-signature classes). Infiltration attacks are slow / low-volume and do not produce the flow-statistics signature CICFlowMeter captures well; a comparative study found infiltration on this dataset is only well-detected via NetFlow-derived features. Deliberately not chased by lowering the threshold (that would spike FPR across every well-detected class). (b) External-validation collapse: models reported "nearly perfect" on CSE-CIC-IDS2018 — which this one's numbers are — have been independently shown to degrade toward random on external/real-world traffic. Plus a dataset-level ~7.5% label-noise ceiling (automatic time-window labeling, not per-flow human verification) this pipeline cannot detect or correct from inside.

3.5   Cortex-Emulation

In plain terms

Emulation analysis runs a sample inside Speakeasy, a lightweight Windows emulator, and records the API calls it makes — a way to observe behavior without letting the sample touch a real machine. A neural network then judges that trace. Testing showed a serious problem: a model trained on samples collected in January 2022 detects only about 42% of malware collected just three months later, and making the model smaller does not help. It also barely beats a trivial lookup table. Because of this, Emulation is trained but kept entirely out of the decision — its verdict is logged for analysis only.

What it detects and why it is a separate signal

Malicious behavior observed in a Speakeasy emulation trace (API-name sequence), before the sample runs on a real host — complementary to Behavioral's real-execution traces.

Dataset & provenance

Quo Vadis (Trizna et al., 2022/2024), HuggingFace dtrizna/quovadis-speakeasy — Speakeasy-emulator-generated malware/benign execution reports. Licence verified explicitly before downloading (Apache-2.0, confirmed via both the HF license tag and the card text). 92,700 files: 75,298 train collected January 2022, 17,402 test collected April 2022 — a deliberate concept-drift split by the dataset's authors, preserved, not re-randomised. ~5.5 GiB.

Architecture chosen, and why

Same family as Cortex-Behavioral — 1D-CNN + multi-head self-attention (models/emulation_cnn.py) — with three deliberate, documented deviations tuned to this data: embed_dim=64 (not Behavioral's 128, because the vocabulary is ~8× larger — 3,152 real API names — with no more training data, so a bigger embedding table would add untrainable dimensions); dropout=0.4 (not 0.3, to resist memorising rare-token patterns); batch_size=64; MAX_SEQ_LEN=500 (p90–p99 of the real sequence-length distribution). Conv/attention capacity kept unchanged as a reasoned starting point (Behavioral's own train set, ~7,340 examples, is the same order of magnitude as this signal's 6,070). 777,345 parameters. Raw sigmoid, no calibration layer (checked: the Platt-calibration bug fixed for Static's ONNX export was LightGBM-predict_proba-specific with no torch-path analogue).

Divergence from the reference: deliberately not the reference GRU / opcode design — the real data has no opcode or memory-access-pattern signal. Modeling population restricted to module_entry rows only; thread / tls_callback_* rows stay in the canonical parquet but are excluded from train/val/test. Within module_entry, exact-duplicate API-name sequences are collapsed to one representative per unique sequence (a duplicate_count column is retained), done separately per era so the concept-drift comparison is preserved.

Split & training

Train 6,070 unique sequences (benign 4,044 / malicious 2,026), val 675 (450/225), test 2,495 (1,936/559). Early stop on val ROC-AUC plus an explicit train/val AUC-gap overfitting monitor (stop if train_auc − val_auc > 0.05 for 3 consecutive epochs). The primary run (embed_dim=64) hit the overfitting stop at epoch 22 (best epoch 19, val AUC 0.9495); val AUC plateaued ~0.94 by epoch 8 while train AUC ran to 0.995 — the model memorises the ~6k collapsed training sequences trivially. Held-out test AUC-ROC 0.8737.

Threshold derivation

EMULATION_MALICIOUS_MIN = 0.999358594417572 — the target-FPR-1% point from the val+test sweep (2,386 benign, pooling Jan and Apr eras, flagged explicitly). For logging / telemetry only. The score distribution is strongly bimodal; at this threshold pooled detection is only ~49.9% (~24 expected FP). The 0.1% target (~2 FP) is too thin to trust.

Current performance and the two disqualifying findings

Finding 1 — ablation-confirmed Jan→Apr concept-drift collapse. At the 1%-FPR threshold, malicious recall drops from 70.7% (Jan-era slice) to 41.5% (Apr-era slice), AUC-ROC 0.949 → 0.874; benign FPR holds ~0.7–1% in both eras, so the loss is entirely malicious-side. Re-running at embed_dim=32 (the overfitting stop's own first recommendation): the stop fired earlier (epoch 18, worse on every axis) and the drift gap did not move — recall 68.0% → 38.3% (29.7 pp gap vs 29.2 pp at embed_dim=64). Capacity reduction fixed nothing — this is a genuine train/test distribution shift, not an overfitting artifact. A per-family diagnostic shows the model memorises token sequences rather than learning generalizable behavior: it fires near what it memorised and goes quiet on modest drift, and for a family with too thin a distinct-sequence base (coinminer: 185 unique train sequences vs ransomware's 1,065) it never builds a firing region at all — coinminer stays ~15–25% detected across every match bucket, including exact train matches.

Finding 2 — thin margin over a trivial baseline. Test accuracy at the 1%-FPR threshold is 86.4% (embed_dim=64) / 85.6% (embed_dim=32), against a majority-class baseline of 77.6% and an exact train-sequence duplicate-lookup of 82.2%. The model beats the lookup table by only +4.1 pp / +3.3 pp.

Disposition — stricter than an ALERT cap

Cortex-Emulation has no branch in decide(). emulation_verdict_from_score() and EmulationVerdict exist for logging only. This mirrors the earlier research repo's own Behavioral v2 category signal (deployment_status: additive_report_only_not_in_policy_decision). A signal that recovers ~40% of malware on the next collection era and barely beats a lookup table cannot carry autonomous or ALERT authority. No ONNX export and no pipeline.py wiring for this signal. A genuine fix would most likely need engineered behavioural-category features (coarser file/registry/network/injection activity classes, hypothesised to be more temporally stable) or training data spanning more collection dates — explicitly not more hyperparameter tuning, which the ablation ruled out.

Section 4

Policy Engine / Decision Logic

In plain terms

The policy engine turns up to five signal verdicts into one final decision. It does this with a strict checklist, top to bottom: the first rule that matches wins. It never averages or blends scores — a weak "maybe" from four signals cannot add up to a strong verdict. The order encodes trust: a Static BLOCK is checked first and is always final; a Behavioral MALICIOUS comes next and can TERMINATE a process; Memory and Network can only ever raise an ALERT, no matter how confident they are; Emulation is not consulted at all. Any error or failed check falls through to ALERT — never to a silent "allow".

Emulation appears nowhere in this chain by design. There is no emulation_verdict == branch.

Design invariants
  • Verdicts, not scores. decide() receives enum verdicts; the numeric scores never enter it. No weighting, averaging, or ensembling anywhere in the decision path.
  • Static BLOCK is always protected. Rule 1 returns immediately; nothing downstream can soften it, and Behavioral is never even run after a BLOCK.
  • Upgrade-only for lower signals. Memory/Network MALICIOUS can raise an otherwise-ALLOW/ALERT outcome to ALERT, but can never reach BLOCK or TERMINATE.
  • Fail-closed. Every ERROR path yields ALERT. The default final decision on the dataclass is ALERT, not ALLOW; ALLOW is only reached by explicitly exhausting every malicious/error condition.
Section 5

Known Limitations and Risk Mitigations

This section is deliberately prominent, not an appendix. Every limitation below is real, documented in the repository, and reflected in how much authority the policy engine grants the affected signal. For each: the risk in plain language, the technical evidence, why the policy engine caps that signal as a direct, evidence-based consequence, and what it would take to lift the cap.

5.1   Memory — single-VM benign artifact

The risk, plainly

The Memory model's benign training examples all come from one baseline virtual machine. The model may have learned to recognise "that specific machine's normal state" rather than "the absence of malicious activity." On a different clean machine it could raise false alarms — or, worse, miss malice on a system that simply does not look like the training VM.

Technical evidence. A single-feature-AUC sweep over all 62 raw+derived features found 22 of them individually exceed 0.95 AUC, confirmed identically on the training split and the never-touched test split (ruling out our own split leaking — separately verified: 0/32,106 sample-id groups and 0/58,596 duplicate feature-vector hashes span splits). Example bands (train): handles.avg_handles_per_proc 208–318 for benign (std 17.5) vs 71–33,784 for malware; dlllist.avg_dlls_per_proc 34.5–53.2 for benign vs down to 7.3 for malware. One derived feature (svcscan_driver_ratio) has 5.8× the gain of the next-best. This pervasive, held-out-stable separability matches CIC-MalMem-2022's documented collection methodology: every benign sample is a repeated capture of "normal user behavior" on a single baseline Windows 10 VM; malicious samples span far more varied executions.

Why the policy engine caps Memory at ALERT. Because the near-perfect held-out metrics (AUC 1.0, recall 1.0) are plausibly an artifact of that single-VM benign collection, they are evidence to keep the cap, not to lift it. An unvalidated signal must not autonomously TERMINATE/BLOCK a process it cannot be trusted to have judged on malice rather than machine identity. Memory still runs as a fully independent signal (not gated behind Static) so it can raise an ALERT on fileless activity.

What would lift the cap. Memory captures from multiple genuinely different, non-baseline benign machines, plus validation against real injected-process samples outside CIC-MalMem-2022's test set. More rows from the same dataset would not qualify. Also open: a way to identify benign near-duplicate capture sessions (only exact duplicates are currently merged).

5.2   Network — Infiltration blind spot & external-validation collapse

The risk, plainly

Two things. First, the Network model is almost blind to slow, quiet intrusions ("Infiltration"): it catches only about one in ten. Second, models that look near-perfect on this particular dataset have repeatedly been shown to fall apart on real-world traffic. So its clean lab numbers should not be read as production-ready.

Technical evidence — Infiltration. Held-out test detection for Infiltration is 10.75% (n_test 1,433) despite 11,463 training rows — every other class with under 10,000 train rows still scored ≥91% (except FTP-BruteForce and DoS-SlowHTTPTest, which are high only because of a near-degenerate duplicate flow signature). This is a CICFlowMeter feature-representation ceiling: infiltration is slow / low-volume by design and does not produce the flow-statistics signature CICFlowMeter captures well; an independent comparative study found infiltration on this dataset is only well-detected using NetFlow-derived features. Lowering the threshold to chase it would spike FPR across every well-detected class.

Technical evidence — external validation. A documented pattern specific to CSE-CIC-IDS2018: models reported "nearly perfect" on it (Cortex-Network's test AUC is 0.9972) have been independently shown elsewhere to degrade toward random performance on external/real traffic. Plus an independently reported ~7.5% label-noise ceiling from the dataset's automatic time-window-based labeling — some fraction of both the training signal and the "ground truth" behind every metric here is simply wrong, undetectably from inside the dataset.

Why the policy engine caps Network at ALERT. Two independent legs, either sufficient alone: (a) the Infiltration gap means Network cannot be trusted alone for slow/quiet threats — but that class is exactly what Behavioral (API sequences) and Memory (process/injection artifacts) have process-level visibility into, so system coverage still holds without giving Network autonomous authority; (b) external-validation collapse means the clean test numbers cannot be assumed to predict field performance. Having both legs is why this cap is treated as at least as firm as Memory's.

What would lift the cap. Independent validation on real network traffic that CSE-CIC-IDS2018 did not generate; and, for Infiltration specifically, a NetFlow-derived feature representation (a documented future option, not applied).

5.3   Emulation — confirmed Jan→Apr concept-drift collapse

The risk, plainly

The Emulation model was trained on samples from January 2022 and tested on samples from April 2022 — only three months apart. Its malware detection fell by roughly 30 percentage points over that gap. Shrinking the model to reduce overfitting did not change this at all, which means the model is memorising specific call sequences rather than learning what malicious behavior looks like. It also barely beats a lookup table.

Technical evidence. At the 1%-FPR threshold, malicious recall drops from 70.7% on the Jan-era slice to 41.5% on the Apr-era slice (AUC-ROC 0.949 → 0.874); benign FPR holds ~0.7–1% across both eras, so the loss is entirely malicious-side. A pre-committed capacity fallback was tested: at embed_dim=32 the overfitting stop fired earlier (epoch 18 vs 22, worse on every axis) and the drift gap did not move — 68.0% → 38.3% (29.7 pp) vs 29.2 pp at embed_dim=64. Per-family diagnosis: coinminer (185 unique train sequences) stays ~15–25% detected in every match bucket including exact train matches — the model never built a firing region for it — while ransomware (1,065 unique train sequences) tracks match quality (exact-match Apr rows 70% detected, near-match only 29%). Mechanism: the model memorises token sequences rather than learning generalizable behavior. Margin check: test accuracy 86.4% vs a majority-class 77.6% and an exact train-sequence duplicate-lookup 82.2% — +4.1 pp over the lookup table.

Why the policy engine excludes Emulation entirely. This is stricter than the Memory/Network ALERT cap: Emulation has no branch in decide() and its threshold is set for telemetry only. A signal that loses ~40% of its malware detection on the very next collection era, with capacity reduction ruled out as the lever, and that beats a lookup table by ~3–4 pp, cannot carry autonomous or ALERT authority. This mirrors the earlier research repo's own precedent for its Behavioral v2 category signal.

What would lift the report-only status. A materially different model, not more tuning: most likely engineered behavioural-category features (coarser activity classes, hypothesised to be more temporally stable than exact API-call token sequences) or training data spanning more collection dates. Then re-assess authority from scratch.

5.4   Static — the recently-found, partially-fixed feature-extraction gap

The risk, plainly

A broken optional import meant one whole group of features (the digital-signature summary) was being filled with zeros for every file scanned live — while the training data had real values there. That mismatch quietly pushed live scores toward "malicious." The import is now fixed, but the live feature extractor still does not perfectly match the reference used to build the training data, and there is no automated test that would catch the next such regression.

Technical evidence. features/pe_features.py imported from signify.authenticode import SignedPEFile, an API removed in the installed signify 0.9.2 (now AuthenticodeFile). The module's except ImportError swallowed the failure, _SIGNIFY_AVAILABLE became False, and the 8-dim authenticode group returned all-zeros for every file at inference — a train/serve skew, because EMBER2024's training vectors carry real authenticode features. It was caught only by manually re-scanning the 5 cortex-endpoint validation files and noticing svchost.exe (a signed Microsoft binary) scored 0.99 where cortex-endpoint scored 0.47. Partial fix applied: ported to the 0.9.x API; svchost.exe now parses a genuine chain (num_certs=1, real countersigning timestamp), and the authenticode group contribution moved from +1.17 (wrongly toward malicious) to −1.33 (toward benign), shifting its score 0.9913 → 0.9839. Not fixed: svchost.exe still does not reach ALLOW (0.9839 vs 0.4744). The residual ~2.0 raw-margin gap is a broader fidelity problem — pe_features.py produces a vector systematically shifted toward "malicious" vs the thrember reference (header pushes harder: +3.75 vs +3.36; benign-side groups softer: histogram −0.51 vs −0.83; the hand-rolled 8-feature authenticode group carries less signal than thrember's even when populated: −1.33 vs −2.12).

What would close it. (2) Close the residual per-group fidelity gap so the live vector stops skewing toward "malicious."

Section 6

Engineering Discipline

In plain terms

Every one of the five signals was built the same careful way: check the data's structure against the actual files, not the documentation (which was wrong more than once); actively hunt for data leakage — where the answer accidentally leaks from the training set into the test set — rather than assume the data is clean; and re-derive every decision threshold from scratch against the model actually trained here, never copy a number from a previous project. This process caught real, score-changing bugs in every signal.

Schema validation against real data, not documentation
  • Memory: CIC-MalMem-2022 validated structurally against the real file — column count, dtypes, exact Class value set, first/last column identity.
  • Emulation: the Quo Vadis dataset card's documented schema is wrong — it describes each file as {"sha256": ..., "entry_points": [...]}; the real files are a bare JSON list with no wrapper and no sha256 field (recoverable only from the filename). One category (report_windows_syswow64, 294 files) uses a completely different filename scheme. The card's own row-count table is off by 3 from the real repository; its prose numbers are staler still. All verified by a full diff against the real file listing.
  • Network: the real S3 bucket structure and the 84-vs-80 column discrepancy were confirmed against the actual CSVs, not assumed from the docs; the label allowlist was built by scanning 16.2M real label values.
Real leakage checks — with the bugs they caught
  • Behavioral: a naive split left 85 sequences spanning multiple splits; fixed with a grouped stratified split keyed on identical api_calls sequences (verified 0 after).
  • Memory: a grouping-detection bug (using only "median group size > 1") treated the constant "Benign" Category as one giant real group and put all synthetic benign rows in one split — caught on a synthetic dataset shaped like the real one before it ever ran on real data. Then, on the real 58,596 rows, 20 duplicate feature-vector hashes (80 rows) spanned multiple splits; fixed with a union-find merge that unions sample-id groups with exact-duplicate-vector groups before allocation, making cross-split duplication structurally impossible.
  • Network: 495,181 / 2,000,000 rows (24.75%) exact duplicates; 4,742 duplicate groups spanning both benign and malicious labels excluded entirely from train/val/test; and a real stratified_group_split index bug (writing into a plain array with non-contiguous index values, "working by coincidence") fixed with reset_index(drop=True).
  • Emulation: 96.8% of entry-point rows were exact duplicates; an early naive split produced a val set that was 90.2% malicious because one 4,312-row duplicate group dominated it. The apihash field was validated rather than trusted — 686 / 6,699 apihash groups (10.2%) were false merges — so the pipeline falls back to a hand-computed sequence hash.
Thresholds re-derived from scratch, never inherited

Every signal's operating threshold is derived against its own trained model's calibrated probabilities — Static (find_threshold_for_fpr() at FPR 0.01 / 0.001 on 539,940 test rows), Behavioral (a sweep on val+test, deliberately not a precise FPR target given only 274 benign), Memory (FPR 0.01 on 5,860 benign), Network (FPR 0.001 on 321,733 benign), Emulation (FPR 1% sweep, telemetry only). None carried over the prior project's placeholder values. The README states plainly: "If you retrain any model from scratch, the raw score distribution will differ and these need to be re-derived again, not assumed to still hold."

Three concrete bugs found and fixed — evidence of process quality

1 · The Platt-calibration bug (Static ONNX export). export_static_lgbm_to_onnx() had been written earlier but never run against the real trained model. First run surfaced that the raw LightGBM booster's output and predict_proba() (which applies a Platt calibrator on top) differ by up to 0.213 on real test data — and the deployed thresholds were derived against the calibrated distribution. Exporting the bare booster would have silently shipped a model whose scores no longer matched its thresholds. Fixed by merging the calibrator's LogisticRegression (via skl2onnx) into the same ONNX graph as the booster (via onnxmltools), chained after a Slice that extracts the malicious-class column. Two further version bugs fixed en route (opset-15 cap hardcoded to 17; IR-version / duplicate-tensor-name mismatches before merge_models). Verified against 10,000 real rows: max abs diff 0.0032, zero verdict differences.

2 · The Memory duplicate-hash leak. On the real 58,596-row dataset, 20 duplicate feature-vector hashes (80 rows, 0.14%) spanned multiple splits — 8 groups / 55 rows benign-only (no per-sample identifier exists for benign rows), 11 groups / 25 rows cross-malware-family collisions (different samples, coincidentally identical coarse VolMemLyzer summary stats). A separate crash was also fixed: verify_zero_duplicate_feature_hashes tried to hash the string split column itself, failing to cast "train"/"val"/"test" to float64. Final verified state: 0/32,106 sample-id groups and 0/58,596 duplicate feature-vector hashes span more than one split.

3 · The signify import break (Static live extraction). features/pe_features.py imported from signify.authenticode import SignedPEFile, removed in signify 0.9.2. The except ImportError swallowed it silently, so the 8-dim authenticode feature group returned all-zeros for every live scan while training vectors had real values — a train/serve skew invisible to offline eval. Caught only by a manual 5-file comparison (svchost.exe scoring 0.99 vs cortex-endpoint's 0.47). Now ported to the 0.9.x AuthenticodeFile API. This is precisely the class of regression an automated feature-parity test would catch immediately — building one is the top open static-path item (§5.4, §7).

  8. CLI packaging. cortex-ml is a Python library, not yet a deployable agent — no packaged CLI (mirroring cortex-endpoint's scan / scan-behavioral / scan-combined surface) and no PyInstaller build. This gap has grown as signals were added. Prior lessons to reapply: exclude torch from the start, watch the matplotlib/PIL transitive dependency, budget for the self-flagging false-positive risk from day one.

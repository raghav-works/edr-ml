Static verdict selection (config/thresholds.yaml, single source
of truth - loaded once at process start)

Static score
    │
    ├── < 0.4789517595186417
    │        └── Static verdict = ALLOW
    │
    ├── >= 0.4789517595186417 and < 0.9811748406902472
    │        └── Static verdict = ALERT
    │
    └── >= 0.9811748406902472
             └── Static verdict = BLOCK  (see step 8 - this is
                 interim-capped, not an autonomous final BLOCK)

Examples:
Static score 0.30  → ALLOW
Static score 0.80  → ALERT
Static score 0.995 → BLOCK (verdict), demoted to final ALERT
                      unless corroborated by memory or network
                      (step 8)

What happens after static scoring?
Static verdict
      │
      ├── ERROR  → skip behavioral entirely, go to step 8
      │
      └── ALLOW / ALERT / BLOCK
             └── proceed to behavioral analysis if a trace was
                 supplied (step 7a). Unlike the earlier design,
                 BLOCK does NOT stop here: a file scoring above
                 the block threshold still gets full behavioral
                 scrutiny, because behavioral MALICIOUS is the one
                 signal that can still escalate a BLOCK-scoring
                 file to TERMINATE, and skipping behavioral on the
                 highest-scoring files would give them LESS
                 scrutiny than a borderline ALERT file gets.

└──────────────────────────────┬────────────────────────────────┘

Sequence-length gate

0 real calls
    └── Behavioral verdict = PENDING  (empty sequence)

1-9 real calls
    └── Behavioral verdict = PENDING  (below this length the model
        is non-discriminative: val+test AUC 0.66, 0 of 4 malicious
        sequences detected - PENDING is the honest answer, not a
        limitation)

10-99 real calls
    └── Score the zero-padded sequence. The verdict is used, but
        a "behavioral_short_trace" reason code is attached, because
        short-trace benign coverage rests almost entirely on one
        training dataset.

Exactly 100 real calls
    └── Score all 100 calls normally.

More than 100 real calls
    └── Score only the first 100. Remaining calls are ignored.

No behavioral_model or tokenizer configured
    └── Behavioral verdict = NOT_PROVIDED (neutral - a config gap,
        not a scan failure)

Behavioral model

│ Input:  100 numerical API token IDs                           │

Behavioral verdict selection
Behavioral score
       │
       ├── < 0.60
       │       └── Behavioral verdict = BENIGN
       │
       └── >= 0.60
               └── Behavioral verdict = MALICIOUS

Examples:
Behavioral score 0.50  → BENIGN
Behavioral score 0.59  → BENIGN
Behavioral score 0.60  → MALICIOUS

The behavioral model does not produce ALERT or TERMINATE directly.
It produces only BENIGN or MALICIOUS. Only the policy engine turns
a MALICIOUS behavioral verdict into a final TERMINATE decision.

Static feature-degradation override (runs AFTER behavioral, on
purpose - a degraded static extraction must never suppress a
caller-supplied API trace, and a completed behavioral MALICIOUS on
the same file still wins in the policy engine regardless of what
happens here):

    any CRITICAL feature group degraded in step 6?
         │
         ├── yes → static_verdict is set aside → ERROR
         │         reason: static_features_degraded
         │         (routes toward NEEDS_REVIEW, step 8)
         │
         └── no  → static_verdict from step 7 stands

signal_health bookkeeping (kept separate from the verdicts
themselves): a configured memory/network model that raised an
exception records "model_error"; features supplied with no model
wired records "model_not_configured" (deliberately neutral - it
does not push the scan toward NEEDS_REVIEW); a degraded static
feature group records "degraded" and lists which group(s) in
degraded_groups.

┌───────────────────────────────────────────────────────────────┐
│ 8. FINAL DECISION LOGIC (first match wins - a strict priority │
│    chain, not a blend)                                        │
└───────────────────────────────────────────────────────────────┘

1. Is the behavioral verdict MALICIOUS?
       │
       ├── Yes → Final decision = TERMINATE
       │
       └── No
             ▼
2. Is the static verdict BLOCK, AND is it corroborated by memory
   MALICIOUS or network MALICIOUS on the same scan?
       │
       ├── Yes → Final decision = BLOCK
       │         (a static-only BLOCK, with no corroborating
       │         signal, can NEVER reach this branch - it always
       │         demotes to ALERT at step 4 below. Corroboration
       │         only unlocks BLOCK; it never lets memory's or
       │         network's own authority exceed ALERT.)
       │
       └── No
             ▼
3. Is the memory verdict MALICIOUS?
       │
       ├── Yes → Final decision = ALERT
       │
       └── No
             ▼
3b. Is the network verdict MALICIOUS?
       │
       ├── Yes → Final decision = ALERT
       │
       └── No
             ▼
4. Is the static verdict ALERT, or BLOCK (uncorroborated)?
       │
       ├── Yes → Final decision = ALERT
       │         (reason code distinguishes "static_alert" from
       │         "static_block_capped_at_alert")
       │
       └── No
             ▼
5. Did any signal (static / behavioral / memory / network) end
   in ERROR - i.e. could not be analyzed at all?
       │
       ├── Yes → Final decision = NEEDS_REVIEW
       │         ("cannot analyze" is not a malware finding, so
       │         this is a separate review queue, not a quieter
       │         ALERT)
       │
       └── No
             ▼
6. Otherwise
       └── Final decision = ALLOW
           reason: no_malicious_evidence

Corroboration flag (audit trail only, never changes the outcome
above): whenever 2 or more of {static ALERT/BLOCK, memory
MALICIOUS, network MALICIOUS} are true on the same scan, the
reason codes gain "corroborated_multi_signal". This never fires
from behavioral alone and never widens memory's or network's own
ceiling past ALERT except through rung 2 above.

Possible final decisions are:

ALLOW         → no active supplied signal produced malicious
                evidence (does not prove every kind of evidence
                was available)
NEEDS_REVIEW  → at least one signal could not be analyzed, and
                nothing else found malicious/suspicious evidence -
                a review queue, not a malware alert
ALERT         → suspicious static/memory/network evidence, or a
                scanner failure needing review
BLOCK         → a static score at/above the block threshold,
                corroborated by memory or network MALICIOUS on the
                same scan (the enum value exists for the
                uncorroborated case too, but that case is currently
                always demoted to ALERT - see step 8, rung 2 and 4)
TERMINATE     → the behavioral model identified malicious API
                activity

Currently, these are only JSON decisions. The package does not
actually allow, block, quarantine, or terminate anything at the
operating-system level.

Not part of the runtime decision: Cortex-Emulation

A fifth model, Cortex-Emulation, is trained and evaluated
(Speakeasy/Quo Vadis traces, same CNN+attention family as
behavioral, first 500 tokenized API calls, threshold
0.999358594417572) but is deliberately never wired into decide().
Its verdict is computed for telemetry and later analysis only,
because a Jan-2022-to-Apr-2022 temporal concept-drift ablation
showed its malicious recall collapsing from roughly 71% to roughly
42% on the later collection period - not stable enough to carry
even ALERT authority yet.

Team-ready explanation

Cortex-ML scores whatever evidence a caller supplies for a single
scan: a file path is required, and an API-call trace, a
memory-snapshot vector, and a network-flow vector are each
optional. Memory and network are scored first and independently of
file validity, because their entire purpose is catching
injected/fileless activity and network-only C2 traffic that has no
file for static analysis to examine. The file path, if given, goes
through path validation, PE-structure validation, a rule-based
known-file allowlist, then 2,568-feature extraction and a
calibrated LightGBM model that yields ALLOW, ALERT, or BLOCK.
Unless static scanning itself failed, a supplied API-call trace is
then tokenized and scored by a 1D-CNN with self-attention, yielding
BENIGN, MALICIOUS, or PENDING for short traces. None of the four
scores are averaged. A single priority chain decides the outcome:
behavioral MALICIOUS always wins and yields TERMINATE; a static
BLOCK only becomes a final BLOCK when corroborated by a MALICIOUS
memory or network verdict on the same scan, and otherwise demotes
to ALERT, because static's own evidence has a documented
false-positive pattern that a second, independent, positive signal
is required to override; memory and network MALICIOUS verdicts are
each capped at ALERT on their own, reflecting how narrow and
lab-collected their validation data still is; and any signal that
could not be analyzed at all - rather than one that produced a
suspicious finding - routes to a separate NEEDS_REVIEW queue instead
of being reported as a malware ALERT. A fifth model, Cortex-
Emulation, is trained and scored for telemetry but is intentionally
excluded from this decision because of observed accuracy collapse
across collection periods. The result is a structured JSON security
event with every score, verdict, reason code, and health flag
recorded; live telemetry collection and actual OS-level blocking,
quarantine, or process termination are not yet implemented.
